# 1. Purpose

This document translates Antar’s domain model into a relational persistence design.

It defines:

- database conventions,
- table ownership,
- primary entities,
- relationships,
- constraints,
- indexing strategy,
- deletion behavior,
- versioning,
- scripture storage,
- reflection persistence,
- reading continuity,
- curated content,
- Saar conversations,
- citations,
- retrieval records,
- and vector embeddings.

This document describes the recommended V1 PostgreSQL model.

It is not a final migration script and does not define Java or JPA classes.

---

# 2. Persistence Strategy

Antar V1 uses:

```text
PostgreSQL
+
pgvector
```

PostgreSQL is the durable source of truth for:

- canonical scripture,
- user accounts,
- reading state,
- reflections,
- curated understanding,
- conversations,
- citations,
- and retrieval metadata.

Redis may cache selected data but does not own durable business state.

---

# 3. Database Architecture

Antar begins as a modular monolith using one PostgreSQL database.

Each domain module retains logical ownership of its tables.

Recommended schema layout:

```text
identity
scripture
reading
reflection
guidance
understanding
saar
search
platform
```

Example:

```text
identity.users
scripture.verses
reflection.reflection_entries
saar.conversations
```

Separate schemas provide:

- clearer ownership,
- reduced naming collisions,
- easier permission control,
- easier future extraction,
- and visible domain boundaries.

A module must not write directly to another module’s tables.

Cross-domain operations should occur through application services or approved query interfaces.

---

# 4. Identifier Strategy

Use UUIDs for internal entity identifiers.

Recommended type:

```text
UUID
```

Primary keys should be generated by the application or database using UUID version 7 when supported by the selected libraries and PostgreSQL version.

UUIDv7 is preferred because it provides:

- globally unique identifiers,
- approximate chronological ordering,
- better index locality than UUIDv4,
- and safe generation across distributed application instances.

Canonical scripture identity should not depend only on UUIDs.

A Verse also has a stable canonical identity:

```text
chapter_number
verse_number
```

The internal UUID remains the database relationship key.

---

# 5. General Table Conventions

Most mutable tables should include:

```text
id
created_at
updated_at
version
```

Recommended definitions:

```text
id          UUID PRIMARY KEY
created_at  TIMESTAMPTZ NOT NULL
updated_at  TIMESTAMPTZ NOT NULL
version     BIGINT NOT NULL DEFAULT 0
```

`version` supports optimistic locking.

Immutable or append-only records may omit `updated_at` and `version` where appropriate.

---

# 6. Time Handling

Use:

```text
TIMESTAMPTZ
```

for all persisted timestamps representing real events.

Store timestamps in UTC.

Convert to the Reader’s local time at the application boundary.

Do not store application timestamps as:

- local timestamp without zone,
- formatted strings,
- or epoch values unless required for an external integration.

Date-only concepts should use:

```text
DATE
```

---

# 7. Text Handling

Use PostgreSQL `TEXT` for:

- scripture,
- translations,
- reflections,
- commentary,
- explanations,
- and Saar messages.

Do not introduce arbitrary `VARCHAR` limits for long-form content.

Use bounded `VARCHAR` only for genuinely constrained values such as:

- language codes,
- short status names,
- external provider identifiers,
- and source slugs.

Application validation should enforce user-facing text limits.

---

# 8. Enumerations

Prefer database `VARCHAR` columns with application-level enums for most lifecycle states.

Examples:

```text
reflection_type
message_role
conversation_status
publication_status
guidance_path
source_type
```

Avoid PostgreSQL enum types in V1 unless the value is exceptionally stable.

Application-managed enums are easier to evolve through migrations.

Use check constraints where corruption would be costly.

---

# 9. Deletion Strategy

## Canonical Content

Scripture and published source content should not use ordinary user-driven deletion.

Corrections should be managed through versioned content workflows.

## User-Owned Content

User-owned data should support explicit deletion.

Prefer hard deletion for:

- reflections,
- drafts,
- conversations,
- bookmarks,
- reading history,
- and account-owned projections

unless retention requirements require otherwise.

Soft deletion should not be added by default.

Soft deletion introduces:

- hidden filtering requirements,
- uniqueness complications,
- privacy ambiguity,
- and accidental reappearance risk.

Where recoverability is required, implement a clearly bounded recovery window rather than universal soft deletion.

---

# 10. Audit Strategy

Application audit data should distinguish between:

1. Business timestamps.
2. Security-sensitive audit records.
3. Operational logs.

Business tables should not become generic audit logs.

Sensitive events may be recorded in:

```text
platform.audit_events
```

Examples:

- account deletion requested,
- privacy preference changed,
- reflection export generated,
- administrative scripture content changed,
- provider credentials rotated.

Audit records should avoid storing unnecessary private content.

# 12. Scripture Schema

Scripture data is canonical, mostly immutable, and read-heavy.

## 12.1 `scripture.chapters`

```text
scripture.chapters
------------------
id
chapter_number
canonical_name
english_name
short_intent
verse_count
publication_status
content_version
created_at
updated_at
```

Constraints:

```text
PRIMARY KEY (id)
UNIQUE (chapter_number)
CHECK (chapter_number BETWEEN 1 AND 18)
CHECK (verse_count > 0)
```

`short_intent` is editorial orientation and not scripture.

It must remain distinguishable from canonical content.

---

## 12.2 `scripture.verses`

```text
scripture.verses
----------------
id
chapter_id
verse_number
canonical_reference
sanskrit_text
content_version
source_package_id
source_package_checksum
publication_status
created_at
updated_at
```

Constraints:

```text
PRIMARY KEY (id)
FOREIGN KEY (chapter_id) REFERENCES scripture.chapters(id)
FOREIGN KEY (source_package_id) REFERENCES scripture.content_packages(package_id)
UNIQUE (chapter_id, verse_number)
UNIQUE (canonical_reference)
CHECK (verse_number > 0)
CHECK (
  (source_package_id IS NULL AND source_package_checksum IS NULL)
  OR (source_package_id IS NOT NULL AND source_package_checksum IS NOT NULL)
)
```

Example canonical reference:

```text
2.47
```

The stored Sanskrit text should preserve:

- Unicode characters,
- punctuation,
- verse markers where approved,
- and editorial formatting.

`source_package_id` / `source_package_checksum` identify which imported package currently
populates Sanskrit for the Verse. They update together with `content_version` on successful
import. Until the first successful import, both are NULL and `sanskrit_text` remains NULL.

**Version history (v1):** prior Sanskrit text is not retained as DB revision rows. Immutable
content-package artifacts (keyed by package checksum) are the durable history source until a
product need for historical Reader views requires a revision table.

---

## 12.2a `scripture.content_packages` and import audit

Implemented by Flyway `V006__create_scripture_content_packages.sql`.

### `scripture.content_packages`

Durable identity for **successfully imported** packages and their editorial lifecycle.

```text
scripture.content_packages
--------------------------
package_id
package_format_version
scripture_id
chapter_number
content_version
package_status          -- editorial: APPROVED | SUPERSEDED | REVOKED
package_checksum        -- UNIQUE
manifest_checksum
provenance_checksum
verses_checksum
source_registry_references
importer_version
first_imported_at
last_verified_at
created_at
updated_at
```

Invariants:

```text
PRIMARY KEY (package_id)
UNIQUE (package_checksum)
UNIQUE (scripture_id, chapter_number) WHERE package_status = 'APPROVED'
  -- at most one active APPROVED package per scripture + Chapter
```

DRAFT packages and failed import attempts are **never** stored here.

### `scripture.content_package_imports`

Durable **execution** outcomes. Editorial `package_status` and execution `import_status` stay
separate.

```text
scripture.content_package_imports
---------------------------------
id
package_id                 -- FK; NULL for FAILED
attempted_package_id       -- always set
package_checksum
chapter_number
import_status              -- IMPORTED | FAILED | REVOKED | SUPERSEDED
records_*
failure_code / failure_message   -- FAILED only; sanitized metadata
importer_version
started_at / completed_at / duration_ms
```

Rules:

- Successful imports require `package_id` FK to `content_packages`.
- FAILED rows keep `package_id` NULL so failures never create active packages.
- `VALIDATED` is transient and not persisted.
- Dry-run writes nothing.
- Do not store local paths, Verse text, package blobs, stack traces, or unsafe exception output.

### Supersession

A higher `content_version` APPROVED package may supersede the prior active package for the same
Chapter in one transaction: mark prior `SUPERSEDED`, register the new package, update Verses,
write `IMPORTED` audit.

```text
content_version
```

```text
source_registry_references
importer_version
first_imported_at
last_verified_at
created_at
updated_at
```

Invariants:

```text

UNIQUE (package_checksum)

  WHERE package_status = 'APPROVED'
```

```text
translation.content_package_imports
-----------------------------------
id
package_id                 -- FK; NULL for FAILED
attempted_package_id
package_checksum
chapter_number
import_status              -- IMPORTED | FAILED | REVOKED | SUPERSEDED
records_*
failure_code / failure_message
importer_version
started_at / completed_at / duration_ms
```

Rules:

- DRAFT packages and failed attempts are never stored in `content_packages`.
- Dry-run writes nothing.
- Do not store local paths, translation body text, package blobs, or stack traces

# 15. Reflection Schema

Quick and Deep Reflection use one aggregate and one primary table.

## 15.1 `reflection.reflection_entries`

```text
reflection.reflection_entries
-----------------------------
id
user_id
verse_id
reflection_type
content
entry_status
created_at
updated_at
version
```

Possible `reflection_type` values:

```text
QUICK
DEEP
```

Possible `entry_status` values:

```text
DRAFT
SAVED
```

Constraints:

```text
PRIMARY KEY (id)
FOREIGN KEY (user_id) REFERENCES identity.users(id)
CHECK (char_length(content) <= configured_limit)
```

Do not create a global uniqueness constraint across:

```text
user_id + verse_id + reflection_type
```

unless the product explicitly limits Readers to one reflection of each type per Verse.

Recommended V1 decision:

- one Quick Reflection per Reader and Verse,
- multiple Deep Reflections allowed over time.

This can be enforced using a partial unique index:

```text
UNIQUE (user_id, verse_id)
WHERE reflection_type = 'QUICK'
```

Deep Reflections remain unbounded by uniqueness.

---

## 15.2 Quick-to-Deep Relationship

A Deep Reflection may begin from a Quick Reflection.

Add an optional self-reference:

```text
origin_reflection_id
```

Constraint:

```text
origin_reflection_id → reflection.reflection_entries.id
```

Business rules:

- the origin must belong to the same Reader,
- the origin must reference the same Verse,
- the origin should normally be `QUICK`,
- converting to Deep Reflection must not silently delete the Quick Reflection.

---

## 15.3 `reflection.reflection_revisions`

Optional V1 capability.

```text
reflection.reflection_revisions

content

```

Possible `change_source` values:

```text
USER_EDIT
```

```text

```

## 15.4 Autosave and Idempotency

Reflection writes should support an idempotency key supplied by the client.

Optional table:

```text
platform.idempotency_records
```

or a request-level Redis mechanism.

The durable Reflection record remains the source of truth.

The API should distinguish:

```text
SAVING
SAVED_LOCALLY
SAVED_TO_SERVER
SYNC_FAILED
```

These are application states and do not all require persisted status columns.

# 16. Journey Persistence

Journey Memory is a projection, not an independent source of Reflection content.

Recommended V1 approach:

- query Reflection entries directly,
- enrich them with Verse context,
- group them chronologically,
- return a Journey projection.

Do not initially create a `journey_memories` table.

Conceptual projection:

```text
JourneyMemory
-------------
reflection_id
verse_id
canonical_reference
reflection_preview
reflection_type
created_at
month_group
```

If Journey queries become expensive, add a materialized or asynchronous projection later.

Potential future table:

```text
journey.journey_memory_projection
```

Any projection must remain rebuildable from source records.

## 19.4 Source Registry Alternative

For stronger referential integrity, introduce:

```text
search.knowledge_sources
```

Every retrievable unit receives one source identity.

Then Citation and Embedding reference:

```text
knowledge_source_id
```

This avoids polymorphic citation references.

This is the recommended design if retrieval is implemented early.

---

## 19.5 `saar.retrieval_runs`

# 26. JSONB Usage

Use JSONB selectively.

Good candidates:

- flexible search projection metadata,
- provider-safe operational metadata,
- source-specific publication metadata,
- and feature configuration.

Avoid JSONB for core domain relationships that require:

- foreign keys,
- uniqueness,
- filtering,
- ordering,
- or strong validation.

Do not store entire aggregates as JSON documents.

# 27. Optimistic Locking

Use optimistic locking on frequently edited mutable aggregates:

```text
identity.users
identity.reading_preferences
reading.reading_progress
reflection.reflection_entries
guidance.guidance_sessions
understanding.articles
saar.conversations
```

A stale update should return a conflict rather than silently overwrite newer data.

This is especially important for Reflection autosave across multiple devices or tabs.

```text
↓

↓

↓

↓
```

# 33. Cross-Schema Foreign Keys

Because V1 uses one PostgreSQL database, physical foreign keys across schemas may be used.

Examples:

```text
reflection.reflection_entries.user_id
    → identity.users.id

reflection.reflection_entries.verse_id
    → scripture.verses.id
```

These improve integrity.

However, application ownership rules remain:

- Reflection writes Reflection tables.
- Scripture writes Scripture tables.
- Identity writes Identity tables.

A foreign key does not grant domain ownership.

If a module is later extracted, cross-schema relationships become external identifiers managed through APIs or events.

# 34. Transaction Boundaries

Use one database transaction for operations that mutate one aggregate and required local consistency records.

Examples:

## Save Reflection

```text
Update ReflectionEntry
+
Append ReflectionRevision, if enabled
```

## Submit Saar Question

```text
Create Reader Message
+
Create Retrieval Run
```

Provider invocation must not hold an open database transaction.

Recommended flow:

```text
Persist Reader Message
Commit
↓
Perform Retrieval and Generation
↓
Persist Saar Message, Citations, and Run Metadata
Commit
```

Failures leave an explicit message or generation status.

# 38. Decisions

The V1 data model adopts the following decisions:

- PostgreSQL is the durable source of truth.
- Domain tables are grouped by PostgreSQL schema.
- UUIDs are used for internal identifiers.
- UUIDv7 is preferred where supported.
- Quick and Deep Reflection share one aggregate and table.
- One Quick Reflection per Reader and Verse is recommended.
- Multiple Deep Reflections per Verse are allowed.
- Journey Memory is initially a query projection.
- Today’s Invitation is derived and not persisted as an aggregate.
- Understanding content is curated, reviewed, and versioned.
- Saar Conversations are Verse-scoped by default.
- Citations belong to Saar Messages.
- Retrieval metadata is stored separately from user-visible messages.
- Search projections and embeddings are rebuildable.
- Soft deletion is not applied universally.
- Optimistic locking protects mutable user-owned records.
- Raw private content is excluded from analytics and audit metadata.

# 40. Migration Strategy

Use a migration tool such as:

```text
Flyway
```

Migrations should be:

- append-only after deployment,
- reviewed,
- reversible through forward corrective migrations,
- owned by the module responsible for the table,
- and tested against representative production-like data.

### Infrastructure-only bootstrap migration

The repository foundation begins with:

```text
V001__initialize_database_extensions.sql
```

That migration is infrastructure-only. It may create PostgreSQL extensions such as `vector` and the approved domain schemas. It does **not** create business tables.

Later module-owned migrations create product tables inside those schemas.

### Later module migrations

Recommended later migration naming:

```text
V002__create_identity_schema_objects.sql
V003__create_scripture_tables.sql
V004__create_reading_tables.sql
```

Alternatively, migrations may be grouped by module while preserving one global ordering strategy. Older planning examples such as `V001__create_identity_schema.sql` describe later product-table work, not the infrastructure bootstrap migration above.

Do not rely on automatic Hibernate schema mutation outside local experimentation.

Production configuration should use schema validation rather than automatic creation or update.

---

# 41. Testing Requirements

The persistence model should be tested using real PostgreSQL through Testcontainers.

Tests should verify:

- unique constraints,
- foreign keys,
- partial indexes,
- optimistic locking,
- deletion cascades or restrictions,
- canonical ordering,
- publication filtering,
- search-vector behavior,
- vector queries,
- transaction rollback,
- account deletion,
- and cross-user authorization assumptions.

H2 should not be treated as an accurate substitute for PostgreSQL-specific behavior.

---

# 42. North Star

Antar’s data model succeeds when it preserves canonical scripture, protects private reflection, supports transparent curated learning, and makes AI behavior explainable without introducing unnecessary infrastructure.

The database should enforce the integrity of the reader’s journey while preserving clear boundaries between:

```text
Scripture
Commentary
Curated Understanding
Reader Reflection
Saar Synthesis
```

No generated convenience should blur those distinctions.
